# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page Vite + React (TypeScript) site presenting a personal family trip-planning itinerary and cost quote, generated from Excel workbooks — the original Europe 2027 trip (`Europa2027_Cotizacion_plan_completo (1).xlsx`, 3 active options) plus a second, independent Orlando/Disney trip (`Plan_Disney_Universal_2027.xlsx`, 2 options). All amounts are per-person COP figures. The UI copy is in Spanish (it's for the traveling family); code and comments are in English.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — typecheck (`tsc -p tsconfig.app.json`) then production build via Vite
- `npm run preview` — preview the production build
- `python3 scripts/generate_data.py` — regenerate `src/data/generated/itinerary.generated.ts` from the Excel workbook (run from the project root; requires the workbook at the repo root)
- `python3 scripts/manage_item.py add|update ...` — add or update a single line item (flight, hotel, tour, SIM card, etc.) directly in the workbook, then regenerates the data file automatically. This is the only supported way to hand-edit a line item — see the `trip-item` skill (`.claude/skills/trip-item/SKILL.md`) for the full field reference and conventions (note ≤ 20 words, optional link, per-person vs. shared amounts, live currency-rate lookups).
- `python3 scripts/update_rates.py` — fetch live EUR/CHF/CZK/USD rates, apply the workbook's own markup factor (`'Tasas de Cambio'!E7`, currently 1.05 = the user's standing "+5%" policy), re-price every line item in every sheet against the new rates, and regenerate the data file. See the `update-rates` skill (`.claude/skills/update-rates/SKILL.md`).
- `python3 scripts/update_climate.py` — refresh each day's sunrise/sunset (exact astronomy) and weather (temperature range + condition, seasonal normals) per exact (city, calendar date) pair actually used across every option, then regenerate the data file. This data lives in Python source (`CITY_CLIMATE`/`CITY_CLIMATE_BY_DAY` in `generate_data.py`), not the workbook, and fetches run in parallel across pairs. See the `update-climate` skill (`.claude/skills/update-climate/SKILL.md`).
- `python3 scripts/generate_brand_assets.py` — regenerate the logo/icon/favicon PNGs from `src/patitours.jpg` (requires Pillow: `pip install pillow`, e.g. in the checked-in but gitignored `.venv/`)

Each day's "Qué llevar" packing tip is computed automatically inside `generate_data.py` (`compute_packing()`) — there's no separate script for it, since (unlike rates/climate) packing guidance doesn't go stale; it's just recomputed fresh every regenerate from that day's `dayKind`/weather/line items. See the `update-packing` skill (`.claude/skills/update-packing/SKILL.md`).

There is no test suite or linter configured.

## Architecture

Data flows one way, in one place, and everything downstream just renders it:

```
Excel workbook  →  scripts/generate_data.py  →  src/data/generated/itinerary.generated.ts  →  App.tsx + components
```

### Data layer (`src/data/`)

- **`src/data/generated/itinerary.generated.ts`** is generated (header says "do not edit manually") by `scripts/generate_data.py`. It is the app's *only* data source — never hand-edit trip options, days, or expenses in a component; fix the workbook or the script instead, then regenerate. It exports:
  - `generatedOptions: GeneratedOption[]` — one entry per active trip option (1 mes por Europa, Italia, Crucero en pareja), each with its full per-day `itinerary`, route, `perPerson`/`total` cost, and `peopleCount`. "Crucero en pareja" is just the display `name` — the underlying workbook sheet and every script's internal `sheet_option` label are still "Solo crucero 2P" (see below), so `--option` in `manage_item.py` takes the *display* name, not that internal one.
  - `exchangeRates` / `ratesUpdatedAt` — the reference exchange rates shown in the UI (informational only; nothing is converted using them at render time — every amount already carries its own converted COP value). Each rate carries a `sourceUrl` (an XE.com converter link, see `CURRENCY_SOURCE_URL` in `generate_data.py`) that `ExchangeRatesCard` renders as a clickable link opening in a new tab; `ratesUpdatedAt` is shown right there too, in the card's "Tasas estimadas · {date}" header — deliberately kept next to the rates rather than duplicated in `AppFooter`.
- `generate_data.py` parses the `.xlsx` directly as a zip of XML (no external dependency), reading each *active* option's sheet by index (sheet4=Completo/"1 mes por Europa", sheet12=Solo crucero 2P/"Crucero en pareja", sheet14="Crucero Milán"/"Italia") plus the `Tasas de Cambio` sheet (sheet3) for exchange rates and the shared traveler count. It keeps only rows whose category matches a fixed whitelist (Vuelos y Trenes, Traslados, Alojamiento, Crucero, Tours y Excursiones, Comidas, Seguro de Viaje, Otros y Extras), drops rows with a blank title (merged-cell formatting leftovers), and drops "N/A" placeholder rows from what's displayed as an expense (see `is_placeholder`) while still using them to keep day continuity (a day with only placeholder lines still gets a card) — a genuine zero-cost item with a real title (e.g. "Tour a pie gratis") *is* displayed, rendered as "Incluido". If the workbook's sheet layout, column order, or sheet-to-option assignment changes, update the script's column-letter mapping (`A`–`M`) and sheet-number list together, then re-run the script.
- `peopleCount` is per-option, not a single global number: sheet4/sheet14's per-person amounts (column K) divide by the shared `'Tasas de Cambio'!$C$5` cell, *except* sheet12 (a duplicate of Solo crucero for 2 travelers — see `scripts/duplicate_option.py`), whose K-column formulas divide by a literal `2` instead. `generate_data.py`'s `options_meta` carries each option's own `people_count`; `manage_item.py`'s `OPTION_PEOPLE_OVERRIDE` does the same for future edits to that sheet. Read the K-column cached values directly rather than assuming a shared divisor.
- `scripts/duplicate_option.py` duplicates an existing option's sheet for a 2-person headcount (used to create sheet12/"Crucero en pareja" from the 3-person cruise sheet) — copies the sheet's worksheet/drawing/rels parts via targeted regex row-surgery (never a full-document XML parse/reserialize on these large sheets; see the module docstring for why), reduces quantity on truly per-person rows while keeping their unit price, and clears bundled/shared-total rows (hotel, SIM, cruise cabin fare, group transfers) to a "Pendiente cotizar" placeholder rather than guessing a new total. It was written for that one duplication; adapt the row classification (`CLEAR_ROWS`) and sheet/rId/drawing numbers for a future one — check the workbook's current max sheet/drawing number and rId first (they must be free). A 4-person sibling (`duplicate_option_4p.py`, sheet13/"Crucero para 4") and 3-person sibling (`Solo crucero`, sheet10/"Crucero para 3") once existed the same way but are now hidden/inactive — see the "now-hidden option sheets" bullet below.
- `scripts/duplicate_option_venice.py` is a different kind of duplication: same headcount as the source (no pricing transform), used to create a brand-new city-anchor option (sheet14, `--option "Italia"`) from an existing one ("Múnich y Crucero", by-then-hidden sheet8) as a structural template — a verbatim copy of the sheet, then every Múnich-specific row (flight, transfer, hotel, tours, meals) is individually re-pointed to new-city content via `manage_item.py` calls, since that's genuinely new content (different flight route, different hotel, different tours) rather than a mechanical transform. Anything without a real quote is left as a `$0` "Pendiente cotizar" row, same convention as the headcount duplicates. When duplicating the whole sheet, double check for rows that already existed identically in the source and now need de-duplicating (e.g. a flight-day "Comidas a bordo" placeholder from earlier per-option work) rather than blindly re-adding one. This particular option was pivoted twice after creation — Venecia → Milán → a two-city Milán-then-Florencia routing (train between them, mid-trip) — before landing on the display name "Italia"; the script's own name and the internal sheet label ("Crucero Milán") are just history at this point, not necessarily the current display name, and don't need to stay in sync with it. `TripSelectionScreen.tsx`'s `OPTION_TITLE_DUCK_BY_NAME` puts a small illustrated duck (not an emoji) next to this specific card's title, keyed by option name — a one-off per-card touch, not a general per-option feature.
- `scripts/duplicate_option_milan_europa.py` was the same kind of duplication as `duplicate_option_venice.py` (verbatim copy, same headcount, no pricing transform), applied to the then-29-day "1 mes por Europa Zúrich" sheet (sheet4) instead of a cruise sheet — it created sheet15 ("1 mes por Europa Milán"), with the opening Zürich segment re-pointed to Milán. Both that Milán variant and the original Zürich opening are now gone (see below) — this script is historical, kept for the row-surgery pattern it demonstrates, not because sheet15 is still active.
- `scripts/restructure_2027_plan.py` is the migration (September 2026) that turned sheet4 into the current "1 mes por Europa": the real Iberia tickets the family bought replaced the placeholder flights (now landing directly in Barcelona instead of via a Zürich opening, and departing from Berlín instead of Múnich), which prompted reshuffling the whole itinerary to start with the cruise and end in Berlín — Barcelona (llegada+tour) → Crucero (Barcelona→Ravenna, 7 noches) → Venecia (1 noche post-crucero) → Roma (3 noches) → París (3 noches) → Praga (3 noches) → Múnich (2 noches) → Berlín (3 noches + día de vuelo de regreso), 25 days total (07–31 May 2027). The Zürich opening (4 days) was deleted outright; the sheet was renamed "1 mes por Europa" (dropping "Zúrich", since that city is no longer part of the trip); internal transport legs whose route changed as a result (Roma→París, París→Praga, Praga→Múnich, Múnich→Berlín) were left as `$0` "Pendiente cotizar" rows rather than guessing a price for the new pairing, same convention as the duplicate-option scripts. `scripts/swap_roma2_for_milan.py` followed right after, replacing that post-cruise Roma stop with Milán (the cruise's own Roma port call, Civitavecchia, stayed put) — its Duomo ticket and Alpine Wonders (Swiss Alps day trip) prices were copied verbatim from "Italia" since both options now visit Milán and those are date-independent fixed quotes (a ticket/tour price, unlike a specific hotel booking tied to specific nights), while the new city's hotel and transport legs again went in as "Pendiente cotizar". Like the other duplicate/migration scripts, both are historical — tailored to their exact before/after, not meant to be re-run.
- Only 3 of the workbook's option-shaped sheets are active (read by `generate_data.py`): sheet4 ("1 mes por Europa"), sheet12 ("Crucero en pareja"), sheet14 ("Italia"). Five more were hidden (not deleted) rather than removed outright when this option list was trimmed down: sheet15 ("1 mes por Europa Milán" — collapsed into sheet4 once its only difference, the opening city, went away entirely), sheet10 ("Crucero para 3"), sheet13 ("Crucero para 4"), sheet6 ("Zúrich y Crucero"), sheet8 ("Múnich y Crucero"). Their real quoted data is still in the workbook if ever needed again — just excluded from `generate_data.py`'s sheet list and `manage_item.py`'s `OPTION_SHEETS`. The workbook has 15 sheets total; besides those 5 and the 3 active option sheets, the rest — `Resumen Comparativo`, `Instrucciones`, `Tasas de Cambio` (read, for rates), and one per-option `Resumen`/`Resumen CZ`/`Resumen Opción 4`/`Resumen Crucero` sheet (in-Excel SUMIF category summaries, never read by the generator) — are also hidden. Whether hidden as an original summary sheet or hidden by this later trim, the rule is the same: ignore them entirely, don't keep them in sync, don't duplicate them when adding a new trip-option sheet, don't treat their numbers as a source of truth.

### Second workbook: Orlando/Disney (`Plan_Disney_Universal_2027.xlsx`)

- A completely independent Excel file (own TRM/exchange rate, own sheet layout), added later for a second family trip (Disney World + Universal Orlando + Epic Universe, Semana Santa 2027) that has nothing to do with the Europa itinerary above. `generate_data.py` reads it in `build_disney_option()`/`read_disney_rate()`, separate from every function above — never route Orlando data through `read_rows()`/`to_expense()`/`manage_item.py`, which are all hard-coded to the Europa workbook's A–M "one row per dated line item" column layout. This workbook's shape doesn't fit that model at all: costs are bucketed per category *and per traveler-type* (adults vs. children — Disney/Universal/food price them differently), with no per-row date; the day-by-day plan instead lives in separate "Itinerario Grupo A/B" sheets keyed by day number.
- Produces exactly 2 options, one per hotel-room subgroup, both real family compositions from the workbook's own "COMPOSICIÓN DE LOS 2 GRUPOS" section: **"Orlando con Jero"** (workbook's "Grupo A" — sheet2 budget + sheet4 itinerary, 3 adults + a 7-year-old) and **"Orlando con Pachito y Vale"** (workbook's "Grupo B" — sheet3 budget + sheet5 itinerary, 2 adults + a 9-year-old + a 13-year-old — the 13-year-old pays adult fare everywhere per the workbook's own notes, so `adults_count=3, children_count=1, has_adolescent=True` for this one, even though its real-world "adults" is 2). `peopleCount=4` for both, matching the workbook's own "Costo por persona (÷4)" convention. The display names (who's on the trip) are just that — display names; the workbook's own "Grupo A"/"Grupo B" sheet names and internal comments/variables still say Grupo A/B and don't need to stay in sync with whatever the family calls each subgroup.
- **Blended per-person pricing in the day/category breakdown, real per-type pricing in the headline.** Disney/Universal/Epic tickets and daily food cost adults and children different amounts — but the invariant that `CategoryBreakdownView`'s and `DayByDayView`'s totals always reconcile (both sum the exact same per-day `amount` fields) assumes one shared per-person divisor. Rather than redesigning that model, each traveler-type cost bucket (e.g. "Tickets Disney World — adultos (3 personas)") is shown *in the day/category views* at its *blended* share of the whole subgroup's total (`bucket_total / peopleCount`, exactly what `to_expense`'s K-column division already does elsewhere) — never at what an adult or the child individually pays there. `build_disney_option()`'s `blended_expense()` helper does this once, consistently, and every such row's `note` states the real per-adult/per-child unit price too, so the blended figure is never a hidden approximation. This is also why the option's headline `perPerson` (a straight sum of every blended row) reproduces the workbook's own "Costo por persona (÷4)" cell exactly — verify that whenever touching this function. The *real* (non-blended) per-fare-type price lives separately in `GeneratedOption.perPersonByType` (`{ label, amount }[]`, e.g. `[{label:"Adulto",...}, {label:"Adolescente (13)",...}, {label:"Niño (9)",...}]` for "Orlando con Pachito y Vale") — computed once at the option level (shared costs like the hotel split evenly per head, fare-specific costs like tickets/food kept at their real per-type rate) so that `adults_count·adult + children_count·child` reproduces the group total exactly, same as the blended figures do. It's optional on `GeneratedOption` (`undefined` for every Europa/Italia/Crucero option, all of which are genuinely homogeneous per-person) and rendered next to the blended headline in both `TripSelectionScreen`'s option cards and `TripSummaryBar`, not instead of it — the blended number is still what the day/category math is built on.
- Where a cost bucket isn't naturally tied to one day (Disney's 4-day/4-park pass, the 8-day food budget, PhotoPass/souvenirs/tips), it's placed on a specific day by convention rather than split proportionally: the Disney tickets go on the first Disney park day (Magic Kingdom); food is a recurring "Comida del día" line on every day except the arrival day (matching the workbook's own "8 días" label exactly — 9-day trip minus the arrival day); PhotoPass/souvenirs/tips are shared bundled costs on day 1, same convention as Europa's SIM-card/insurance rows. The round-trip flight is split the same way as Europa's Iberia booking: full round-trip fare on the arrival day, "Incluido" ($0) on the departure day.
- **`GeneratedDay` has two Orlando-only fields**: `planNote` (the itinerary sheet's bulleted ride-by-ride plan for that day, rendered as `.day-plan-note` in `DayByDayView.tsx`) and `planNoteCaption` (a short height/age caveat, e.g. "TRON requiere 48\" — verificar altura del de 9 años"). Both are `null` for every Europa/Italia/Crucero day — `build_itinerary()` always sets them to `None`, so the type stays a plain `string | null` rather than optional, and nothing needs a fallback check when reading them there.
- Orlando's own `CITY_INFO`/`CITY_IMAGE_POOLS`/`CITY_CLIMATE` entries are single static values (no per-day precision, no `CITY_CLIMATE_BY_DAY` entries) — reasonable seasonal estimates for Semana Santa (late March), not run through `update_climate.py` (which is itinerary-shaped for the Europa trip's per-day astronomy/weather lookups, not a fit here). Refine by hand if asked, following the same `CITY_CLIMATE` dict shape.
- The Disney workbook's own TRM (`Resumen!B6`, currently 3120 COP/USD, read live by `read_disney_rate()`) is deliberately **not** the same rate shown in `ExchangeRatesCard`'s footer (which only ever reflects the Europa workbook's `Tasas de Cambio` sheet) — Orlando prices won't exactly match if a reader cross-checks against that footer's USD rate. Flagged here since it reads like an inconsistency at a glance; it isn't one, both rates are real and independently sourced.
- Two Excel quirks the script corrects for, which will resurface if the workbook is edited by hand again:
  - Some sheets store the date column as a raw Excel serial number instead of formatted text (`normalize_date`/`excel_serial_to_text`) — always cross-check a fresh export's date column before assuming it's already a string.
  - `Seguro de Viaje` rows carry a coverage-period date range (e.g. "29 Abr – 30 May … cobertura"), not an itinerary stop — it's treated as dateless (like `Otros y Extras`) and attached to day one, rather than parsed as its own day.
- The script derives each day's city from its lines' `place` text via `CITY_ALIASES`/`day_city` (prioritizing that day's `Alojamiento` entry, then falling back to substring-matching known city names, then carrying forward the previous day's city) — there is no separate hand-maintained per-day city list. `CITY_INFO` supplies the cosmetic country/emoji/image per canonical city name; adding a new destination means adding it to both `CITY_INFO` and `CITY_ALIASES`.
- A day's `dayKind` (`'flight' | 'embark' | null`, also computed by the script) marks the outbound-flight day and the cruise-embarkation day so the UI can show a plane/boat icon instead of the destination's country flag for those two transit days — see `getDayDisplayLabel` below.
- Each day also carries `climateCity`/`sunrise`/`sunset`/`temp`/`weatherIcon`/`weather`/`packing`/`weatherUrl`/`sunUrl`, shown in `DayByDayView`'s `.day-conditions` row and packing popup. Values come from `CITY_CLIMATE_BY_DAY` (per exact `"{climateCity}|{dayKey}"`, refreshed by `scripts/update_climate.py`), falling back to the per-city-only `CITY_CLIMATE` and then `DEFAULT_CLIMATE` for any day not yet covered. `weatherUrl`/`sunUrl` (per `climateCity`, from `CLIMATE_SOURCE_URL`/`SUN_SOURCE_URL`) are what the weather chip and the sunrise/sunset chips link to, opening in a new tab — same "Ver fuente" treatment as the currency links below. `climateCity` is usually the same as `city`, but diverges on a day-trip day (e.g. 02 May is a Zürich-based day with a Tours line up to the Jungfraujoch) — see `day_trip_destination()`/`DAY_TRIP_DESTINATIONS` in `generate_data.py` and the `update-climate` skill's "Day trips" section. The day's own `city`/`title`/hero image are never affected, only the weather block; the UI shows a small "Clima de {climateCity}" note when the two differ.

### App layer (`src/`)

- **`main.tsx`** is the bootstrap only (mounts `<App />`). All state and composition lives in **`App.tsx`**.
- **`App.tsx`** owns the UI state (selected trip option, current view, selected day/category, mobile menu) and composes the presentational components below. It contains no formatting or data-shaping logic — that lives in `utils/`.
- **`types.ts`** — the `Category` union (must stay in sync with `CATEGORY_BY_EXCEL` in the generator script) and `ViewMode`.
- **`constants.ts`** — `CATEGORY_META`: icon, color, and a `duck` sticker per category, shown in the "Por rubro" cards (`CategoryBreakdownView`). Every category has a duck; two (Comida, Seguro) have no exact thematic match among the available stickers, so they use the closest fit rather than a literal one — see the comment there before swapping one out. `icon` (the emoji) is still what's used for the small per-expense icon in the day view.
- **`hooks/useTheme.ts`** — light/dark theme state; see "Brand assets and theming" below.
- **`utils/currency.ts`** — `formatCOP` and `formatExpenseAmount`. Every non-COP expense is always rendered as *original currency · COP equivalent* (e.g. "€ 75 · $ 281.295") — never add a path that shows only the converted COP figure for a foreign-currency line.
- **`utils/dayDisplay.ts`** — `getDayDisplayLabel`, which turns a day's `dayKind` into the ✈️ "Vuelo" / 🛳️ "Embarque" override described above.
- **`utils/tripStats.ts`** — `sumExpensesByCategory` and `collectExpensesByCategory`, the two aggregations behind the "Por rubro" view. Both read straight from a trip option's `itinerary`, which is also what the day view renders — so the two views and the summary total can never drift out of sync with each other.
- **`utils/duckStickers.ts`** — `assignDuckStickers`, the small decorative duck shown on each day's hero photo in `DayByDayView`; see "Brand assets and theming" below.
- **`components/`** — one file per UI section, each a plain presentational component (props in, JSX out, no data fetching):
  - `AppHeader`, `AppFooter` — chrome. `AppHeader` also hosts `ThemeToggle`.
  - `ThemeToggle` — the light/dark switch button.
  - `TripSelectionScreen` — the landing screen (welcome copy + the 4 option cards). Picking a card both selects the option and enters the planner in one step.
  - `PlannerHeading` — the "back to selection" bar shown once inside the planner.
  - `ExchangeRatesCard` — reused by both of the above; takes the occupancy-note copy as a prop since the wording differs slightly between the two places it appears.
  - `TripSummaryBar` — the route + per-person-price bar shown above both itinerary views.
  - `DayByDayView` — the "Por día" tab: day list + selected day's hero/expenses, with a small duck sticker overlaid on the hero photo when one fits.
  - `CategoryBreakdownView` — the "Por rubro" tab: compact category cards (icon + name + total, no other filler) and a drill-down detail panel that opens as a true centered popup (with a click-outside-to-close backdrop) at every screen width — it is not inline content, don't reintroduce a non-modal fallback for narrow viewports.

### Brand assets and theming

- **`src/patitours.jpg`** is the source-of-truth logo lockup (flat JPEG, white background, icon + "PATITOURS" wordmark). `scripts/generate_brand_assets.py` derives everything else from it into `src/assets/brand/`: a transparent-background full lockup and an icon-only crop, each in a light-ink (navy) and dark-ink (cream) variant, plus `public/favicon.png`. Never hand-edit those generated PNGs or design new ones by hand — replace `src/patitours.jpg` and re-run the script. `AppHeader` picks the light/dark logo variant based on the active theme. (Only the full lockup, light and dark, is actually imported anywhere in code today — the icon-only crops are generated and available but currently unused, same as several `src/assets/ducks/*.png`; that's fine, they're not dead *code*, just an unused asset sitting in the library.)
- Theming is CSS custom properties, not two parallel stylesheets. `src/styles.css` defines every color as a `--token` in `:root` (light values) with overrides in both `@media (prefers-color-scheme: dark)` (pre-JS default) and `:root[data-theme="dark"]` (explicit, wins either way). `src/hooks/useTheme.ts` resolves the initial theme (stored choice, else OS preference), writes `data-theme` onto `<html>`, and persists explicit choices to `localStorage`; `ThemeToggle` in the header flips it. When adding a new color anywhere in the app, add a token pair (light + dark value) rather than hardcoding a hex — a hardcoded color will look right in light mode and wrong (or invisible) in dark mode.
- The header is intentionally light in both themes' "chrome sense" — i.e. it always matches the logo's native context (light ink on a light bg, or the recolored light-ink-on-dark variant in dark mode) rather than the old fixed dark-navy bar. If you redesign the header, keep this pairing: the logo variant and the header background token must change together.
- **`src/assets/ducks/*.png`** are the app's small decorative "traveling duck" stickers (not the logo, not emoji) — reach for one here before adding an emoji duck or new artwork. They're final, hand-cropped, checked-in assets; there is no generator script or source sheet in the repo for them anymore. They came from four source sheets, each deleted once fully cropped (at the user's request, to avoid keeping large unused source images around):
  - `patitos.png` — a 6×7 sheet of ~42 activity stickers (`duck-paris.png`, `duck-gondola.png`, `duck-airplane-window.png`, ...).
  - a 4×3 "Catálogo de Patitos Viajeros" catalog (12 travel-style cards) — cropped into `duck-romantic.png` (the "Romántico" card, used in the footer) and `duck-cat-*.png` (`duck-cat-food.png`, `duck-cat-family.png`, `duck-cat-mountain.png`, ...; see the `GRID`/`COLS`/`ROWS` values used when this was cropped if a similarly-laid-out sheet ever needs slicing again). `duck-cat-food.png` is what `Comida` uses in `CATEGORY_META` — none of the first sheet's 42 fit "food" at all, this catalog's "Gastronómico" card does.
  - `patos.png` — a second 40-sticker activity sheet (uneven grid: 5 rows of 6 cutout stickers plus 2 wider rows of 5 multi-duck group scenes) — cropped into `duck2-*.png` (`duck2-map.png`, `duck2-diving.png`, `duck2-family-3.png`, ...). The `duck2-family-*`/`duck2-couple-paris` group shots are what the "N personas" badge on each trip-option card uses (`PEOPLE_DUCK_BY_COUNT` in `TripSelectionScreen.tsx`, keyed by headcount — 2 → `duck2-family-car.png`, 3 → `duck2-family-3.png`, 4 → `duck2-family-4.png`).
  - a third 54-sticker sheet (6×9 grid, plus one row of 5 wider multi-duck group scenes at row index 7 with custom, hand-eyeballed column boundaries — not an even 6-column split like the other rows) — cropped into `duck3-*.png` (`duck3-ski.png`, `duck3-rain-city-umbrella.png`, `duck3-beach-lounger.png`, `duck3-group-cruise.png`, ...). This is the sheet `getWeatherDuck`/`getTourDuck` (below) draw from for weather- and activity-themed stickers.

  All four sheets' cards have a baked-in illustrated or cutout-with-white-border background (not transparent) — style these as small rounded badges/stickers, not rotated transparent cutouts. If a new duck crop is ever needed, it has to be sourced from a freshly re-saved sheet — there's nothing left in the repo to re-slice.
- `src/utils/duckStickers.ts` maps a day's `dayKind`/`city` to a *pool* of matching ducks (not a single fixed one) for the small sticker shown on its hero photo (`DayByDayView`); `assignDuckStickers` walks the whole itinerary picking, for each day, the first pool candidate that differs from the previous day's duck — every pool must have ≥2 entries or that guarantee breaks. Cities with no good match are left out on purpose rather than forcing one.
- `src/utils/weatherDuck.ts`/`src/utils/tourDuck.ts` each assign a duck for every day at once (`assignWeatherDucks`/`assignTourDucks`, same pool-and-rotate shape as `assignDuckStickers` — every situation maps to a *pool* of ≥2 candidates, walked in order so a long run of similar days, e.g. this itinerary's mostly-"Nublado" weather or a 5-day Múnich stay, never repeats one fixed duck) shown side by side in the "Qué llevar" popup (`.packing-modal-ducks`) — deliberately two *different* ducks, not the same one twice, and neither ever overlapping `duckStickers.ts`'s hero-photo pools, `CATEGORY_META`, the headcount badges, or the footer duck (both files' own top comments list the full reserved set) — this popup sits right next to the hero sticker, so reusing one of those ducks would show the identical image twice in the same view.
  - `assignWeatherDucks` — each day's pool is keyed primarily off the `weather` label (so it updates automatically whenever `update_climate.py` refreshes that field, no extra wiring needed), but a freezing low (`temp`'s low end under 5°C) wins over the label regardless of what it says — otherwise a cold-but-not-precipitating day like the Jungfraujoch's "Parcialmente nublado" would show the same neutral pool as any other cloudy day, hiding how cold it actually is.
  - `assignTourDucks` — each day's pool priority: cruise embarkation, flight, the Jungfraujoch train, a day at sea, then a Tours-line keyword match (a Pisa excursion, a free/walking tour, a food/chocolate tour), then `CITY_TOUR_POOL` (a landmark/cultural duck pool for cities that have one in the library — Paris/Eiffel Tower, Roma/Colosseum, Venecia/gondola, Barcelona/flamenco — checked by `day.city`, so it applies to any day spent there, not just tour days), then a generic touring/arrival/exploring pool. Cities without a landmark pool (Zúrich, Zadar, Salerno, Praga, Berlín, Múnich) fall through to the generic pools rather than forcing a mismatched sticker.

### WhatsApp AI assistant (`netlify/functions/`)

The site itself is still a static build (`vite build` → `dist/`), but `netlify/functions/twilio-whatsapp-webhook.mts` is a Netlify Function (deployed alongside the static site — this project is hosted on Netlify, per `netlify.toml`) that answers WhatsApp questions about the trip using Twilio's WhatsApp channel + Gemini. It is a separate concern from the React app above — it reuses the same generated trip data as its source of truth, but has no UI and isn't part of the Vite build. (A brief detour through the Meta Cloud API directly, and before that a version of this Twilio integration that replied via Twilio's Messages REST resource, are both gone — see `git log` on this file if that history is ever needed again.)

- The reply goes back as **TwiML in the webhook's own HTTP response** (`<Response><Message>...</Message></Response>`, `Content-Type: text/xml`) — Twilio delivers it from that, no separate API call needed. This matters: a plain `client.messages.create(...)` call to Twilio's Messages REST resource requires the account's compliance/KYC (Trust Hub) approval to send WhatsApp messages, which replying via TwiML does not. Because the response body *is* the reply, this can't be a Netlify **background** function (whose return value is discarded) — it runs synchronously at path `/api/twilio-whatsapp-webhook`, which is fine since a Gemini flash-lite reply comfortably finishes inside Twilio's ~15s webhook timeout and Netlify's ~10s sync limit.
- It validates Twilio's `X-Twilio-Signature` header (`twilio.validateRequest`, via `TWILIO_AUTH_TOKEN`) against the parsed `application/x-www-form-urlencoded` body (read via the standard `Request.formData()`, since Netlify Functions v2 hand you a Web-standard `Request`) — this is a local HMAC check, not a Twilio API call, so it isn't gated by compliance status either. An invalid signature gets a `401`.
- `netlify/functions/_lib/tripContext.ts` builds the AI's system prompt directly from `generatedOptions` (`src/data/generated/itinerary.generated.ts`) — every option, day, price, and weather value the assistant can talk about comes from there, never hand-duplicated. If it's ever answering with stale info, regenerate the data (see Commands above), not this file.
- `netlify/functions/_lib/db.ts` stores conversations/messages in Postgres (Neon, via `@neondatabase/serverless` over plain HTTPS — reads `DATABASE_URL`/`POSTGRES_URL`) for conversation history and to dedup Twilio's webhook retries by `MessageSid` (stored in the generic `whatsapp_message_id` column). Netlify has no built-in Postgres add-on, so this has to be an external database (e.g. a free Neon project) with its connection string pasted into `DATABASE_URL`.
- `netlify/functions/_lib/gemini.ts` calls the Gemini API with that system prompt + conversation history and returns the reply as-is — there's no human-handoff path yet (the assistant is a travel advisor for now, not a salesperson); `tripContext.ts`'s system prompt tells the model to answer travel-related questions outside the trip data from its own general knowledge (visas, plugs, packing, etc.) while staying on topic, and to ask which trip option the customer means before answering anything else if that isn't established yet in the conversation, then keep using it as the default context (naming it in each reply) until the customer clearly asks to switch. `GEMINI_MODEL` defaults to `gemini-flash-lite-latest` — an alias Google keeps pointed at the current lightweight Flash model, not a pinned snapshot, since a pinned one (`gemini-2.5-flash`) already 404'd once when Google retired it.
- `netlify/functions/_lib/twilio.ts` is now just `verifyTwilioSignature` — no REST client, since nothing here calls Twilio's API.
- Required env vars are listed in `.env.example` — set them in the Netlify UI (Site configuration → Environment variables), not in a committed file. Never log `TWILIO_AUTH_TOKEN` or `GEMINI_API_KEY` in plaintext, and never expose them to the client bundle — they're server-only and read via `process.env` inside the function.
- `tsconfig.api.json` typechecks `netlify/functions/` separately from the app (`tsconfig.app.json` only includes `src/`) since it targets Node with Web-standard `Request`/`Response` types, not the browser DOM; it's referenced from the root `tsconfig.json` but not part of `npm run build`, which only typechecks the app. Netlify bundles each function itself at deploy time (esbuild, per `netlify.toml`'s `node_bundler`) — this tsconfig is purely for local/editor typechecking.

### Keeping this consistent

- If you add a new expense category or trip option shape, update it in the generator script first (`CATEGORY_BY_EXCEL`, `CITY_INFO`/`CITY_ALIASES`, `options_meta` in `main()`), regenerate, and only then touch `constants.ts`/components if the new category needs its own icon/color.
- `src/styles.css` is a single global stylesheet (not co-located per component). It's been swept of rules with no matching class in the JSX — if you remove a class from a component, grep the CSS for it and delete the now-dead rule rather than leaving it behind.
- `src/assets/` is organized by subfolder, not a flat dump — `brand/` (logo/icon variants) and `ducks/` (sticker crops) so far. Put a new image asset in an existing subfolder if it fits, or create a new one; don't add loose files directly under `src/assets/`.
